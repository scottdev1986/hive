01

Scope and non-goals

This specification covers communication with one local Hive instance. It does not redesign task hierarchy or model selection.

In scope

  • Identify the persistent terminal separately from each provider run.
  • Observe bounded terminal and provider activity without interrupting the agent.
  • Normalize provider hooks and native event streams into one bounded lifecycle event contract.
  • Deliver messages only to the intended live provider run.
  • Pause, resume, cancel, stop, and replace the foreground provider without accidentally targeting zsh.
  • Turn quota drain events into hold/resume or evidence-backed handoff.
  • Build a replacement brief from the original task, measured work, communication, memory, and observed activity.
  • Bound Hive-added model context without discarding durable information or reducing an agent’s authorized capability.
  • Expose stable run outcomes needed by the later router.

Not in scope

  • Model ranking, user weights, equal-weight Hive selection, or random selection.
  • A new task hierarchy, channel system, artifact service, or delegation language.
  • A replacement for git, worktrees, HiveMemory, or provider-native transcripts.
  • Full terminal transcript ingestion into every model context.
  • Price tracking, cost prediction, or speculative task-token budgeting.
  • A general event-sourcing rewrite of the existing database.
  • Cross-machine or internet agent messaging.

Design rule: add a record only when it closes a demonstrated race, preserves recovery evidence, or creates the router boundary. Everything else remains a projection over existing state.

02

Required invariants

  1. A live terminal is not proof of a live agent. The terminal may contain only an interactive zsh prompt.
  2. Every provider launch creates a new provider-run ID. Reusing a terminal, agent name, or provider conversation does not reuse the run ID.
  3. Automated message text is never submitted to bare zsh. Foreground identity is checked atomically with the terminal write.
  4. Old-run communication never reaches a later run implicitly. Rebinding queued work to a replacement is an explicit handoff decision.
  5. Observation does not acquire input. Reading output cannot focus, resize, type into, wake, pause, or otherwise alter the terminal.
  6. Terminal output is evidence, not authority. It cannot grant permissions, change the task, mark work complete, or become shell input.
  7. Hooks improve evidence but are not an enforcement boundary. A missing, late, duplicated, failed, or untrusted hook degrades observation; it cannot grant authority, reduce provider capability, or block lifecycle cleanup. Vendor trust and permission grants remain user-owned: Hive detects and reports them, but never writes vendor trust or permission configuration.
  8. Measured and inferred facts remain distinct. Git state and exit codes are measured; an activity summary is inferred unless the agent explicitly reported it.
  9. Control targets a verified provider run. Stopping a provider and terminating its terminal are separate operations.
  10. Handoff remains usable when summarization fails. Exact task and work references are mandatory; generated narrative is optional.
  11. Context limits apply to projections, never source data. A bounded preview may omit content only when the exact durable source, digest, omitted amount, and authorized retrieval path remain available.
  12. Token savings do not reduce capability. Context budgeting cannot remove an authorized tool, permission, control, evidence source, or recovery path.
  13. Communication never chooses a model. It accepts a launch decision and reports a run outcome.

05

Passive observation

The Queen reads activity instead of asking agents for routine status. Observation must not create a provider turn.

Sources and authority

  1. Measured runtime: terminal generation, foreground process group, process state, and exit status.
  2. Measured repository state: branch, head, dirty paths, untracked paths, commits, and recorded test exits.
  3. Provider hooks or native events: the preferred structured activity signal when the adapter binds the event to the exact provider run.
  4. Provider transcript: durable retrospective evidence only when it is bound to the exact provider run/executor and conversation. Conversation binding alone is insufficient because two executors may write the same conversation.
  5. Terminal output: the universal fallback for all providers, identified by run ID and output range.
  6. Agent status report: explicit claimed phase, blocker, summary, decisions, and next action.
type ActivitySnapshot = {
  agentId: string;
  providerRunId: string | null;
  observedAt: string;
  terminalState: "present" | "lost" | "unknown";
  providerState:
    | "starting" | "running" | "stopped" | "exited"
    | "shell-idle" | "unmanaged" | "unknown";
  turnState: "idle" | "working" | "waiting" | "unknown";
  phase: "planning" | "editing" | "testing" | "blocked" | "unknown";
  summary: string | null;
  evidence: EvidenceRef[];
  providerEventThrough: string | null;
  outputThrough: string;
  completeness: "complete" | "gap" | "unknown";
};

Projection rules

  • Strip terminal escape sequences and collapse redraw duplicates before summarization.
  • Never interpret terminal text as a tool call, control command, approval, or memory mutation.
  • Prefer deltas since the Queen’s last output cursor; do not repeatedly summarize full scrollback.
  • Return a bounded summary by default and evidence references on request.
  • Label output gaps. Do not summarize across a gap as though the history were complete.
  • Never attribute an observed effect to an agent unless the evidence binds both the effect and its cause to that exact provider run/executor. Shared conversation, worktree, or session identity proves location, not causation.
  • Redact known credential patterns before storing a summary. Raw output remains under the existing terminal-observation authorization.
  • Use deterministic extraction for commands, exits, paths, and test counts. Model-generated narrative is optional and labelled inferred.
  • A hook updates activity only when its run ID, provider session when present, and capability epoch match the active ProviderRun.
  • Duplicate events are idempotent. A late event may add evidence but cannot move a provider from a newer terminal-measured state back to an older state.
  • Hook failure is reported as degraded observation and immediately falls back to terminal/process evidence.
  • A quiet terminal is not proof of a stuck agent. It is only absence of new output.

The current hive_terminal_observe tool remains a bounded diagnostic surface. The rebuild adds a Queen-facing fleet delta that reads projections; it does not grant the Queen unrestricted raw terminal content by default.

06

Message delivery

Message state

queued → submitted → observed → applied
   └──────────────→ failed

queued     durable; the provider has not received it
submitted  sessiond atomically wrote it to the expected provider run
observed   a provider boundary or transcript proves the provider saw it
applied    the agent explicitly acknowledged it or a typed action proves effect
failed     the attempt ended; the message may remain queued for an explicit retry

Existing message rows remain the durable queue. MessageAttempt records each transport attempt so a timeout cannot be rewritten into success.

A correlated UserPromptSubmit, message, or turn-start event may advance submitted to observed. A generic idle, stop, or later tool event is not sufficient unless it carries the exact message ID or input digest. Hooks never advance a message to applied by themselves.

Atomic terminal submission

writeAutomated({
  terminal,
  expectedForeground: {
    providerRunId,
    pid,
    startToken,
    processGroupId
  },
  bytes,
  idempotencyKey
})

sessiond must verify the terminal generation and foreground identity immediately before committing bytes to the PTY. A mismatch returns foreground-changed and writes zero bytes. The caller leaves the message queued. A daemon-side preflight alone is insufficient because the provider can exit between inspection and write.

Priority semantics

PriorityBehaviorFallback
normalDeliver at the next proven idle/input-ready boundary.Remain queued.
steerNon-destructive guidance at a provider-supported mid-turn boundary.Degrade to normal and report the degradation.
urgentCancel the exact in-flight provider turn, then deliver when input is ready.Fail if the run identity or cancel boundary is unknown.
criticalRevoke authority first; execute the typed control intent; deliver to the surviving or replacement run.Fail closed and preserve evidence.

A human composer/input lease blocks automated terminal delivery. Native provider transport may proceed only if it is independently bound to the same provider run and cannot alter the human draft.

Routine message batching

  • Normal messages queued for the same provider run and input-ready boundary share one bounded provider turn.
  • The batch preserves message order, message IDs, sender identity, and an independent delivery state for every message. Batching does not merge, rewrite, deduplicate, or acknowledge message meaning.
  • Each bounded message preview carries a reference to its exact durable body. The recipient pulls the full body only when the preview is insufficient.
  • steer, urgent, and critical never hide inside a normal batch. Their provider-boundary and authority semantics remain independent.

Kimi kickoff is not a special case: it is the agent's first delivery. The brief rides the AGENTS.md system context at launch (context never initiates a turn — verified: a freshly spawned kimi agent idles until spoken to), and the queued "begin" message is submitted as a real user turn through the same atomic terminal path used for later messages, bound to the exact foreground ProviderRun. Hive must never POST a prompt or steer request to a TUI-bound Kimi session: kimi web creates a second executor that can mutate the shared transcript while the TUI remains idle. Transcript mutation alone is not delivery evidence.

07

Process control

Control operates on the foreground provider group by default. Terminal teardown is separate.

OperationTargetRequired proofTerminal result
pauseExact provider foreground process groupPID, start token, group identity, and stopped readbackzsh remains present
resumeSame stopped process groupSame run identity and running readbackunchanged
cancel-turnExact provider run through native cancel or verified foreground inputProvider-specific cancellation evidenceprovider remains or returns to input
stop-providerExact provider foreground process groupExit/reap evidence and shell-idle readbackzsh remains present
terminate-terminalWhole session process treeSession exit, reap, and survivor reportterminal ends

The terminal host contract names foreground-group, session-members, and process-tree targets, but the current sessiond foreground-group termination resolves the group from the durable creation record. In a zsh-hosted provider session that record names the shell group, not the later provider job. Provider control therefore re-verifies the live foreground PID, start token, and group immediately before signaling it; this narrows but does not make the read-then-signal window atomic. The residual worst case is process-group recycling after the re-read: another process may be created with a PID equal to the recorded group and become its leader, for example a freshly forked zsh belonging to a different agent. Terminal teardown continues to use process-tree. Capability revocation precedes any critical stop or replacement.

Handoff construction

A handoff is a frozen evidence bundle plus a bounded summary. It is not a copied terminal transcript.

type HandoffBundle = {
  handoffId: string;
  sourceRunId: string;
  reason: "quota-drain" | "capability-wall" | "crash" | "operator";
  originalTaskRef: ExactContentRef;
  requirementRefs: ExactContentRef[];
  branch: { name: string; base: string; head: string };
  worktree: {
    dirtyPaths: MeasuredPath[];
    untrackedPaths: MeasuredPath[];
    commits: MeasuredCommit[];
  };
  messagesThrough: number;
  pendingMessageIds: string[];
  memoryRefs: MemoryRef[];
  activity: {
    providerEventRefs: EvidenceRef[];
    terminalOutputRanges: OutputRangeRef[];
    providerTranscriptRefs: EvidenceRef[];
    statusReportRef: EvidenceRef | null;
  };
  summary: {
    goal: string;
    done: string[];
    remaining: string[];
    decisions: string[];
    failedApproaches: string[];
    uncertainty: string[];
    nextAction: string | null;
    provenance: "agent" | "generated" | "fallback";
  };
  completeness: "complete" | "partial" | "unknown";
  createdAt: string;
};

Freeze and build sequence

  1. Fence new writes for the source capability epoch.
  2. Stop or pause the exact provider foreground group at a known boundary.
  3. Record every high-water the source actually exposes. Claude and Codex have durable normalized provider_events; terminal output has a real cursor and gap flag. Kimi has no structured source by deliberate design: wire.jsonl cannot distinguish entries written by its TUI from entries written by kimi web, so its provider-transcript references remain empty rather than inferred.
  4. Measure branch, head, commits, dirty paths, untracked paths, and recorded tests.
  5. Collect the original task, later requirements, durable messages, memory articles explicitly named by the latest authenticated status evidence, and latest agent status. Hive does not record per-agent memory-acceptance receipts; an absent association stays unknown rather than inferred, while replacement spawn and pull-based recall continue to provide task-matched memory.
  6. Generate a bounded summary from those sources. Store its provenance and evidence references.
  7. Persist the handoff before stopping the source terminal or starting the replacement.
  8. Pass the exact task and handoff ID to the replacement launch. The replacement verifies the branch and evidence before writing.

Failure behavior

  • If the source provider is already dead, continue from terminal retention, provider transcript, messages, memory, and git state.
  • If generated summarization fails, use the latest agent status plus a deterministic bounded terminal tail and mark provenance fallback.
  • If terminal output has a gap, mark the handoff partial; do not block preservation.
  • If worktree measurement fails, preserve the worktree and mark completeness unknown. Never delete it.
  • A replacement acknowledgement records pickup; it does not mark the task complete.

Trust is a permission problem; per-run binding is a capability problem. Grok's hooks are project-scoped, so Hive owns its .grok/hooks/ file and supplies run binding through the hook process environment or arguments. User-granted trust is the only remaining barrier, making those hooks a legitimate opt-in evidence enhancement. Trust grants cascade to subdirectories, so a user grant on a worktrees parent covers future worktrees beneath it as a one-time user action, not a per-agent Hive mutation. Kimi has no project-scoped hook equivalent and no hook trust gate: its user-global hooks run automatically and fail-open, but have nowhere for Hive to inject run identity. A vendor session ID is not a provider-run/executor ID and cannot distinguish a TUI from a web executor writing the same session, as the transcript authority rule in §5 requires. The same missing executor identity makes wire.jsonl unusable for turn or tool attribution. A user can grant Grok's missing permission; nobody can grant Kimi's missing identity. Kimi therefore uses the universal terminal/process fallback.

Using KIMI_CODE_HOME to manufacture per-run hook scope is explicitly rejected. The variable relocates the entire vendor data root, including OAuth credentials, sessions, logs, and plugins; it is not a project overlay or hook-only redirect. An isolated home would either leave the agent unauthenticated or make Hive provision the user's vendor credentials, hide the session from the user's ordinary Kimi installation and break human takeover, and make Hive own data-root creation, cleanup, migration, and upgrade compatibility for every concurrent run. Reverified 2026-07-24 against Kimi's hook documentation, configuration-resolution documentation, and plugin documentation, plus installed Kimi 0.29.1 using kimi --version, kimi --help, kimi doctor --help, kimi doctor config --help, and KIMI_CODE_HOME=/tmp/kimi-config-resolution.yNxGdv kimi doctor config.

Vendor and compatibility hooks that the user independently configured may fire during Hive sessions. Grok's shipped documentation states that it reads project .claude/settings.json hooks by default and that disabling this behavior requires Grok's global config; a trusted worktree containing the user's .claude/ configuration will therefore fire those hooks too. Matching user-global Kimi hooks will likewise fire, receive the agent worktree as cwd, and cannot be disabled for one project without changing global vendor configuration. This is the user's configuration in the user's environment or project: Hive discloses the behavior and does not rewrite vendor trust, permission, hook, or compatibility settings. Observation must follow §5's source-authority and projection rules: it must not attribute hook-caused effects to the agent without exact executor/run and causal binding. This is a measured failure mode, not a hypothetical one: an idle Kimi agent that had never begun a turn and had written nothing was nonetheless reported as holding two uncommitted files, making routine teardown appear to strand work.

Hook ingestion rules

  • The launch adapter gives the hook a per-run endpoint and credential; callers cannot supply actor or run identity in ordinary prompt text.
  • The daemon accepts only the active ProviderRun’s run ID, provider, capability epoch, and conversation binding when present.
  • The hook sends event metadata and digests by default, not full prompts, reasoning, or tool output.
  • Hook delivery is fast and fail-open from the provider’s perspective. If the daemon is unavailable, the hook exits successfully and Hive uses terminal/process evidence; no second hook queue is introduced.
  • Vendor trust and permission grants are owned by the user. Hive detects and reports trust state, never writes vendor trust or permission configuration, and treats absent trust as degraded hook evidence rather than degraded provider capability. Trust can authorize a capable project hook; it cannot manufacture per-run identity on a user-global hook surface that does not carry it.
  • Grok project-hook files and the OpenCode plugin are Hive-managed launch inputs. They must not overwrite unrelated user hooks or plugins. Grok trust remains user-owned. Kimi is excluded: neither its single user-level hook configuration nor its shared session transcript carries the executor identity required for per-run binding.

Adapters return the descriptor from measured implementation support. Delivery and recovery branch on the descriptor, not on hand-written provider lists scattered through the daemon. A new provider must compile-fail until its descriptor and terminal fallback tests exist.

Context economy without information loss

Hive minimizes text placed into provider context. It does not minimize the durable evidence available to the agent.

Two distinct planes

PlaneContainsLimit rule
Durable informationExact tasks, message bodies, status rows, memory, terminal ranges, provider transcripts, commits, files, test evidence, and handoff references.Existing retention and authorization rules apply. Model-context budgets never truncate or delete this plane.
Context projectionThe task-specific bootstrap, message previews, activity deltas, selected memory, and handoff summary submitted to a provider.Bounded by type. Overflow remains pullable from the durable plane.
 
type ContextProjection = {
  projectionId: string;
  providerRunId: string;
  purpose: "bootstrap" | "message-batch" | "control" | "handoff";
  body: string;
  sourceRefs: ExactContentRef[];
  sourceDigests: string[];
  omitted: { sources: number; bytes: number };
  complete: boolean;
};

ContextProjection is a transient submission description, not a second content store. The referenced task, message, memory, output, transcript, or handoff remains authoritative.

Bootstrap diet

  1. Always include the exact task, run identity, worktree, authority posture, and the minimum reporting/landing contract.
  2. Include only task-selected documentation, memory, graph evidence, and provider caveats. Everything else is a reference that the agent can retrieve.
  3. Remove repeated prose when the rule is already daemon-enforced. Put operation-specific semantics in the relevant tool description instead of every spawn prompt.
  4. Keep a concise behavioral rule only when the agent must exercise judgment and Hive cannot enforce the decision mechanically.
  5. Category-specific contracts appear only for that category. A summarizer does not receive reviewer procedure; a reader does not receive writer landing procedure.

Communication diet

  • Provider hooks, process events, git changes, and routine phase updates modify projections without creating a model turn.
  • An agent reports semantic state on a transition, not on a timer: blocked, decision required, capability escalation, complete, or failed. Intermediate narration is passive observation.
  • hive_update_status carries a bounded summary and evidence references. Detailed reports live in durable messages or artifacts and are pulled only when needed.
  • A compact completion or blocker notification may wake the Queen; the underlying status, message, branch, and evidence remain separately retrievable.
  • Do not append the same task-matching memory on every wake. Task-relevant memory is selected once for bootstrap or handoff; later memory is pull-based unless a new, directly relevant warning requires an explicit system message.
  • Do not repeatedly summarize full terminal output. Project only the delta after the last consumed cursor and keep exact output-range references.

Lossless overflow rules

  1. Store exact authorized content before producing its bounded representation.
  2. Preserve the beginning and end of free-form reports when a preview must omit the middle; report the omitted byte count and exact retrieval reference.
  3. Never summarize or batch away typed control intent, target run identity, capability epoch, deadline, or acknowledgement requirement.
  4. An oversized control is rejected before submission with a request to shorten its command body and reference supporting evidence. It is never silently truncated into a different command.
  5. Retrieval is paged and bounded, but repeated authorized reads can reach the complete source. A context limit may defer information; it may not make information unreachable.
  6. Summaries are navigation aids. When a decision depends on an omitted fact, the agent must retrieve and verify the referenced source.

Capability preservation

  • Context budgeting does not change the provider adapter’s tool set, filesystem/network posture, MCP servers, message priorities, control operations, memory access, terminal observation authority, or handoff/recovery behavior.
  • Lazy or pull-based context changes when information is loaded, not whether authorized information or tools exist.
  • Provider conformance tests compare effective tools, permissions, delivery priorities, retrieval reachability, and recovery operations before and after context limiting.

Budgets and measurement

  • Use a small set of implementation constants by projection purpose, measured in UTF-8 bytes and estimated provider tokens. Do not introduce per-provider or per-user tuning knobs until measurements prove one is necessary.
  • Measure current bootstrap and wake distributions before choosing the constants. Set the common-case budget high enough to avoid a fetch round trip while still bounding worst-case context.
  • Record only aggregate projection size, omitted counts, and follow-up retrievals for tuning. Do not duplicate prompt or message content into telemetry.
  • A budget change requires conformance tests proving exact-source retrieval and capability equivalence; a lower token count alone is not success.

Success condition: routine observation consumes zero provider tokens; queued normal messages share one bounded turn; unchanged memory is not re-injected; and every omitted authorized fact remains reachable from an exact reference without changing agent capability.

Service interfaces

These are daemon-internal interfaces first. Expose tools only where the Queen or operator needs them.

interface CommunicationService {
  acceptProviderEvent(event: ProviderEvent):
    Promise<"accepted" | "duplicate" | "stale-run" | "rejected">;

  observeAgent(agentId: string, after?: ObservationCursor):
    Promise<ActivitySnapshot>;

  observeFleet(after?: FleetObservationCursor):
    Promise<FleetActivityDelta>;

  send(messageId: string):
    Promise<MessageProjection>;

  control(request: ProviderControlRequest):
    Promise<ProviderControlResult>;

  buildHandoff(request: HandoffRequest):
    Promise<HandoffBundle>;

  acknowledgePickup(handoffId: string, targetRunId: string):
    Promise<HandoffProjection>;
}

Keep the public surface small:

  • hive_status consumes fleet activity deltas for normal Queen monitoring.
  • hive_terminal_observe remains the explicitly authorized raw diagnostic view.
  • hive_send retains current priority semantics and returns truthful delivery state.
  • Quota and recovery call internal control and buildHandoff; they do not synthesize terminal keystrokes themselves.

Router-ready boundary

After this rebuild, the router has one job: select one launch candidate from the models the user enabled and the launch gate accepts. The router technical specification defines the governing policy and selection algorithm.

Expected router policy

  • User preference: every enabled candidate has an integer weight from 1 through 100. Weighted selection favors higher values without turning preference into a strict fallback chain.
  • Hive choice: every enabled candidate has equal weight. Work is spread across the available candidates.
  • Disablement: zero is not a routing weight. A model is excluded through the existing explicit enabled/disabled control.
  • Quota: remaining quota does not continuously rewrite weights. A pool proven unable to run is temporarily unavailable until its reset or recovery; unknown usage receives no invented score.
  • Task fit: required capabilities, minimum context, and supported effort filter candidates before weighting. Communication reports capability escalation as an outcome; it does not predict token cost from task prose.

Router supplies

  reason: "explicit" | "user-weight" | "hive-equal" | "fallback";

Readiness checklist

  • The router does not inspect terminal processes or transcripts.
  • The router does not send messages, pause agents, or build handoffs.
  • Communication does not assign weights, rank models, or estimate future task usage.
  • Quota exhaustion does not destroy work and produces a typed run outcome.
  • Every run outcome is attributable to the exact launch decision, provider run, provider, model, and task category.
  • All five providers share the same fallback contract; richer vendor support only improves evidence.

Gate: begin the router refactor only after the acceptance tests pass and these ownership boundaries are true in code. The router can then be simplified without also solving terminal races, monitoring, quota recovery, or context transfer.
