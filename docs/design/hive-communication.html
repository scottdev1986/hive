02

Status and authority discipline

The labels below describe demonstrated properties of the implementation, not intent.

  • PROVENA terminal generation, a provider run, and an agent are separate identities. Test: test/daemon/db.test.ts — persists each provider execution as a distinct run and closes it once.
  • PROVENTerminal text contributes a bounded inferred summary and never creates authority. Test: test/daemon/activity-snapshot.test.ts — terminal text never becomes authority and gaps remain visible.
  • PROVENA declined or failed terminal write leaves the durable message queued and records the attempt. Test: test/daemon/orchestrator-lifecycle.test.ts — a foreground change leaves the opening message queued with its terminal receipt.
  • PROVENCritical intent revokes the capability epoch before control recovery. Test: test/daemon/control-messages.test.ts — critical revokes the capability epoch before restart and rejects stale acknowledgement.
  • UNPROVENEnd-to-end observation is claimed to be passive. Unit tests demonstrate pure snapshot construction, but proving production passivity requires tracing a fleet observation and showing no input claim, delivery row, provider turn, or quota spend caused by that read.

06

Message delivery

PROVENDurability, terminal submission, vendor receipt, and semantic application are separate states.

Lifecycle state

StatusStateExact meaning
PROVENqueuedThe message row exists. No transport receipt has promoted it. It may be waiting for idle, a tool boundary, input ownership, a live run, or retry.
PROVENinjectedThe terminal host returned a written receipt, the native provider control accepted delivery, or the root protocol accepted input. It does not prove the model read the content, complied, acknowledged, or stopped.
PROVENagent-acknowledgedThe addressed agent called acknowledgement with the required epoch. This may still precede application for non-critical messages.
PROVENappliedAn explicit applied acknowledgement, critical acknowledgement, root inbox consumption, or a recipient-owned turn/transcript boundary after injection closed the receipt loop. src/daemon/delivery.ts: acknowledge, reconcileInjected.

Atomic run-bound write and attempts

PROVENMessageDelivery.deliver records MessageAttempt, passes terminal generation plus PID/start-token/process-group expectation, and wraps text in bracketed paste plus carriage return. HostCore.submitInput re-reads the PTY foreground group and the exact PID identity immediately before the arbiter orders bytes. A mismatch returns foreground-changed with no byte range; the row remains queued.

PROVENAttempt outcomes are pending, written, foreground-changed, input-busy, timeout, or unknown. A late result cannot rewrite a settled timeout. src/schemas/message-attempt.ts; DB timeout test in §04.

08

Quota drain, hold, and resume

PROVENThe drain handler classifies exhaustion and chooses hold, preservation, or handoff notification.

  • PROVENA measured reset within one hour pauses the exact run and stores held, reason, reset time, and held run ID. Test: §R4: a drain resetting within the hour holds the agent, and the sweep pokes it past the reset.
  • PROVENResume first refreshes provider quota, then re-reads held state, active run ID, capability epoch, and verified foreground control. The wake uses an idempotency key; overlapping sweeps produce one durable wake. Tests: the two near-reset tests in test/daemon/drain-handler.test.ts.
  • PROVENA distant reset or an unmetered rate-limit error enters the handoff seam. If every route is drained, the handler can wait for the nearest five-hour reset or retain work and write episodic memory. Tests: the distant, all-drained, and unmetered cases in test/daemon/drain-handler.test.ts.
  • NOT IMPLEMENTEDAutomatic replacement excluding the drained pool is absent. replaceWithHandoff emits a durable notice with provider, pool, reset time, and handoff ID. Implementing replacement requires quota/selection ownership to enforce that exclusion and supply a replacement launch decision.
