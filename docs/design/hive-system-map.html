Separation of concerns — the verdict

Short version: the plane boundaries are real and mostly hold. The terminal plane states its own scope in source and refuses work outside it; the vendor plane has exactly one interface; authorization is one file. What blurs is concentrated in three places — the daemon's HTTP file, one vendor's machine-global hook, and names that outlived the things they named.

Where the boundaries are clean holds

1. The terminal plane declares what it does not own — in the code, not a doc

Every sessiond leaf carries an explicit ownership header. pty_host.zig: “Does NOT own VT parse, checkpoint, attach protocol, or broker grants.” terminal_state.zig: “Does NOT own: input arbitration, process kill, viewer grants, PTY open/spawn.” session_host.zig: “this module implements only the host process and its launcher.” This is the strongest separation in the system, because it is enforced where it is stated.

native/sessiond/src/pty_host.zig:1-5 · terminal_state.zig:1-13 · session_host.zig:1-4

2. Five vendors, one interface

AgentAdapter is “the one provider boundary used by normal agent creation,” and the registry maps all five providers to it. The spawn spine hands an adapter a write-only AgentTurnInput and “never inspects what is sent” — vendor keystroke semantics stay inside the adapter.

src/adapters/providers/provider-adapter.ts:44-60 · provider-registry.ts:9-15

3. Routes are handed decisions, not the authority to decide

The attach-grant route takes three authorization callbacks rather than the capability store, with the reason written down: “passing the store would hand a route the authority to decide what it is allowed to do.” Four roles, one allowlist file, one gate.

src/daemon/session-host/attach-grant-endpoint.ts:20-26 · capabilities.ts:1-2,23,430-460

4. One writer for hierarchy state, three independent fences

“The daemon is the only writer.” hierarchyRevision, runEpoch and capabilityEpoch are checked independently — a stale value of any one rejects even when the other two match — and epochs advance only through their dedicated methods.

src/daemon/hierarchy-store.ts:1-21

5. The knowledge plane degrades instead of leaking

Graphify runs keyless from a scrubbed allowlist environment with --code-only, by absolute path into Hive's own bundle, never on PATH. Its server is held (not detached) so it dies with the daemon, and when it is down a spawn attaches nothing rather than an unreachable URL. Memory embeddings are local ONNX with no automatic fallback: AVAILABLE or UNAVAILABLE, never a fabricated vector.

src/adapters/graphify.ts:1-19 · daemon/graphify-service/graphify-service.ts:1-14 · daemon/memory-embeddings.ts:1-12

6. Lifecycle authority is landing where the rulings put it

The crash-recovery sweep's outcome type is now "reported" | "skipped" — the dead arm is gone. Kill still means positively terminating a process tree and then looking again, because “a signal delivered is an act; a process gone is a state.” And sessiond's one autonomous kill is scoped to processes, never records: it fires only when the daemon that launched the host has been observably absent for a full 90 s, and “unobservable is NOT absence.”

src/daemon/recovery/recovery-service.ts:27-29 · resource-management/teardown.ts:1-14 · native/sessiond/src/host_core.zig:405-462,1325-1336

Where the boundaries blur watch

A. Two vendors have a private door into the daemon's largest file

server.ts is 5,901 lines and imports vendor-specific CLI modules directly: CODEX_TUI_APPROVAL_KEYS from codex-cli and readLiveGrokModel from grok-cli. That is the control plane reaching past the AgentAdapter boundary that exists for exactly this purpose. Two of five vendors are special-cased at the top of the HTTP surface; the other three are not. This is the clearest layering violation on the map.

src/daemon/server.ts:18-19 (vs. the boundary at adapters/providers/provider-adapter.ts:44-60)

B. Kimi's hook surface is machine-global; every other vendor's is not

Hive's only Kimi hook lives in ~/.kimi-code/config.toml, because “Kimi reads hooks only from this user-level config.” The hook is therefore generic and per-agent identity rides the launch environment — a deliberate mitigation, and the right one. But the file itself is $HOME-keyed, so production, dev and QA Hives share one hook block, and so does every ordinary Kimi session on the machine. Compare grok: a worktree-local, instance-hashed hook at <worktree>/.grok/hooks/hive-<hash>.json, with Hive explicitly declining to write ~/.grok/config.toml or trusted_folders.toml. Kimi is the outlier and the cause is a vendor constraint, not a Hive choice — but the blast radius is real and belongs on the map.

src/adapters/providers/kimi-cli.ts:55-59,200-204,218-233 · grok-cli.ts:170,271-277,321,395-396

C. Two generation counters, and only one of them is fenced

Stated in source, at the mail tool boundary: “Hive keeps two generation counters with two different writers, and they agree until they do not; the broker fences on exactly one of them, and this is where that one is read.” Ownership of which epoch is authoritative is not settled in one place — it is settled per call site. Cross-cutting state with no single owner is exactly the shape that passes every test until either counter rotates.

src/mail-service/mail-tools.ts: MailLiveGenerationLookup

D. Instances are separated in Hive's state and joined in their vendors'

HIVE_HOME isolates the database, worktrees, runtime sockets and the QA rig. Provider credential and session stores are keyed to $HOME instead — ~/.claude, ~/.codex, ~/.grok, ~/.kimi-code — so prod, dev and QA agents read and write the same vendor sessions and rollout files. The QA rig documents this as its one deliberate hole: “the real HOME remains available to provider credential stores.” Hive therefore treats provider credential isolation as unavailable rather than implying the per-instance runtime boundary extends to vendor-owned stores.

src/adapters/providers/kimi-cli.ts:55-59 · grok-cli.ts:543-545 · qa/README.md:45-47

E. The input arbiter enforces user-priority, not zero-injection

The arbiter refuses automation while a user claim stands (error.HumanOwned) and refuses delivery into an unstable or absent composer. It does not refuse automation outright: Provenance.automation with action .deliver or .submit is an encoded, size-capped write. The standing “no TUI injection, ever” invariant therefore lives above this layer as policy, not below it as a mechanism — worth knowing before treating the arbiter as the enforcement point for it.

native/sessiond/src/input_arbiter.zig:41-48,73-76,100-108,144-147

Sources and how they were used

Ground truth is the repo. Every box and every edge above was read out of source — imports, socket paths, spawn argv, HTTP route tables, Zig module headers. Where a design doc and the source disagreed, the source won and the disagreement is written up in the blurred-boundary section.

  • docs/design/agentic-hierarchy.html — H1–H5, landed. The plan's own §8 audit (:415-439) finds the hierarchy clauses accurate and the lifecycle clauses stale; this map draws the hierarchy, not the stale lifecycle clauses.
  • src/mail-service/store.ts and src/mail-service/service.ts — the mail lane, lease, and settlement behavior drawn here.

One standing caveat. This map is the landed state at the commit it was written against: native vendor TUIs inside a PTY, one sessiond host per agent. The terminal plane is under an announced architecture pivot — Hive rendering the terminal itself, with vendor binaries remaining the execution and auth truth over a protocol. That design is in revision and is deliberately not drawn here; when it lands, the PTY edge and the vendor-process band are the parts of this diagram that change.
