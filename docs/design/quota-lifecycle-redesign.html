QUOTA LIFECYCLE REDESIGN · REVIEW DRAFT · 2026-07-24

Quota lifecycle · current state vs. dictated policy

Quota stops launches today. Tomorrow it only stops work.

Hive’s quota system is an extensive measurement stack whose only enforcement point is the spawn gate: it can refuse to start an agent, but once an agent runs, quota does nothing but bookkeep and warn. The dictated policy inverts that — never block a spawn, always handle the mid-work drain — and in doing so makes most of the measurement stack’s booking machinery dead code.

Decision · dictated by the user

Never refuse a spawn for usage. Handle exhaustion where it actually happens: mid-work.

Refresh at boot and every 15 minutes and at every agent close. When a provider drains: hold-and-poke if a window resets within the hour, hand the branch to another provider otherwise. When everything is drained: wait out a near reset, or preserve the branch and write a memory.

Scope: src/daemon/quota*.ts · spawner-impl.ts · server.ts — plus one new hold/handoff path

01 · Current state

What the quota system does today, measured against the code.

Every claim below is a file:line in the tree as of 2026-07-24. The short version: measurement is thorough and wired; actuation is one gate and some messages.

When readings are fetched

Boot: a forced refresh of every registered probe at daemon start — but fire-and-forget, so the first spawn can race it (src/daemon/server.ts:1543-1551, refreshQuota at server.ts:1710-1713). Probes are registered per vendor at src/cli/daemon.ts:265-286 (codex/claude/grok/kimi stdio+HTTP).

Cadence: the 30-second maintenance sweep calls needsRefresh() (server.ts:1917-1924), which re-reads when the last refresh is older than refreshIntervalMinutes — default 15 minutes (src/schemas/quota.ts:192) — or when a routable pool has “gone blind” because its window’s reset passed (src/daemon/quota.ts:1228-1246). Inside a refresh, hasFreshReading skips providers already live in both windows (quota.ts:1203-1214).

Event-driven: codex rate-limit notifications ride the app-server event stream (quota.observeCodexRateLimits, quota.ts:450, wired at src/cli/daemon.ts:297-300); claude statusline observations land via observeStatusline (quota.ts:2208, wired at server.ts:3793).

Nothing today refreshes on agent close. Killing an agent settles its reservation (server.ts:2560-2567) and nothing more.

How quota influences spawning

The launch gate itself (src/daemon/authorized-launch.ts:58-80) runs five checks — resolution, enablement, availability, capability-floor, effort — and none of them is quota. Quota enters only afterwards, in routeAndReserve (src/daemon/quota.ts:1645), called for explicit pins (spawner-impl.ts:2361) and for chain selection (spawner-impl.ts:2456).

routeAndReserve can refuse: unbound model-scoped pools put a model in “explicit-pin only” quarantine (quota.ts:1671-1702); a model whose every metering pool is spent fails hasRoom (quota.ts:915-951) with per-category reserve floors (15% 5-hour / 20% weekly, src/schemas/quota.ts:196-197); a launch-failure cooldown holds routes back (quarantinedUntil, quota.ts:865-912). Selection is spread (default: rank-biased by remaining headroom) or strict (rank order) (spawner-impl.ts:2380-2385). A candidate with no measured pool is admitted in “compatibility mode” — unconstrained, with a warning and an alert (quota.ts:1860-1878).

The walk is category chain → default chain → remaining enabled models, and only when all refuse does the spawn fail with every reason listed (spawner-impl.ts:2527-2542). A successful pick creates a reservation with an estimated cost (quota.ts:1879-1887, estimateFor at quota.ts:780).

Mid-work exhaustion: what happens today

Nothing structural. A running agent whose provider drains is not paused, not held, not killed, and its deliveries are not gated. Turn boundaries settle accounting (server.ts:5229-5242: markStarted on session/turn-start, reconcile on turn-end, cancel on dead). Threshold crossings fire an alert (alertPool, quota.ts:2471-2529; warning at 25% / critical at 10% remaining with 5% hysteresis, src/schemas/quota.ts:194-195) which is delivered as a message to the queen (server.ts:1121-1123, delivery.send("hive-quota", ORCHESTRATOR_NAME, …)) — and her brief merely tells her to summarize quota warnings to the user. The agent keeps burning. The queen may react; the system does not.

Stale and unavailable readings today

Probe failure records the reason and alerts once per outage, re-arming on recovery (quota.ts:1066-1084, alertProbeFailure at quota.ts:2435-2459); the last good reading stays in the ledger with its provenance and ages honestly. A model with no measured pool spawns unconstrained (compatibility mode, above) with an explicit “headroom unknown” alert (alertUnknown, quota.ts:2403-2432) — unknown never blocks, and unknown is never filled in with an invented number. On the billing display path, a 30-minute TTL memory serves the last real reading at its true age (readBillingWithMemory, src/daemon/usage-credits.ts:592-697). The only estimates anywhere are labelled cost guesses for future runs (estimateFor, quota.ts:780-794).

The candid read: almost none of this is dormant. The over-engineering is not dead code, it is actuation asymmetry — a large booking apparatus whose only teeth are “don’t start” and “tell the queen a number.” The dictated policy deletes the first and automates the second, at which point most of the booking apparatus genuinely does become dead weight (§05).

02 · Target policy

The dictated rules, as one decision flow.

Verbatim policy, structured for review. “Window” is always the provider’s own 5-hour or 7-day quota window.

R1 / BOOTFresh readings from every provider at start

No stale numbers at boot: the boot refresh is a startup gate for the quota picture, not a background task that races the first spawn.

R2 / CADENCERefresh every 15 minutes, and on every agent close

The existing 15-minute cadence stays; an agent closing is a new refresh trigger (its last spend is only knowable afterwards).

R3 / SPAWNNever deny a spawn because of usage

Agents run all the way down to zero. Quota may still rank candidates (pick the pool with the most room); it may never block one.

R4 / DRAIN ≤ 1hHold, then poke on reset

A mid-work agent whose provider drains holds in place when a window resets within the hour; at reset, Hive proactively tells it to continue — it will not resume on its own.

R5 / DRAIN > 1hHand the branch to another provider

A capable provider’s agent picks up the drained agent’s branch and continues; the drained agent is closed down.

R6 / ALL DRAINEDWait, or preserve and remember

No provider has usage left: wait for the nearest 5-hour reset, or the 7-day reset if it lands within 5 hours. Further out: preserve the branch and write a memory so work resumes when availability returns.

R7 / API DOWNEstimate from last known numbers

When a provider API is down, drain decisions may use the last known readings as estimates — a user-ruled exception to the never-invent posture, for this case only.

Invariant conflicts to rule on

“Never deny for usage” vs. the consent boundary. No conflict — but the line must be drawn in the code review, not left to taste: enablement (the user’s per-model click) and capability gates stay as refusals; only pool-exhaustion refusals die. The gate (authorized-launch.ts) already separates these cleanly.

R7 vs. “unknown, never invent.” This is the one real weakening of a load-bearing invariant. It is tolerable because it is narrow (drain decisions only, provenance-stamped, user-ruled) — but it should live in exactly one function with a comment naming this ruling, so the exception cannot leak into spawn admission or billing by copy-paste.

What the policy deliberately does not say

Selection ranking survives: “never deny” does not mean “ignore headroom” — spread-by-remaining-quota is still the fairest dispatcher, it just can’t say no. Alerts to the queen survive as information; they are no longer the only response. Recovery, delivery, landing, and the terminal stack are untouched.
