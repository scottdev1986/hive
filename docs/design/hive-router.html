H Hive
ROUTER REFACTOR · TECHNICAL SPECIFICATION · 2026-07-24

Model routing · post quota lifecycle and communication rebuild

Preference without lock-in. Distribution without hidden scoring.

The new router chooses one exact provider, model, and effort from a task’s eligible candidates. User mode applies integer relative weights. Hive mode gives every candidate equal weight. A smooth weighted scheduler prevents random streaks, while quota and communication handle proven drain, hold, and handoff outside the selection algorithm.

Core decision

Filter facts first. Distribute second. Launch through one gate.

No ordered fallback ladder, quota-headroom score, inferred model strength, price model, task-token prediction, or outcome-learning loop belongs in the router.

Selection unit: exact provider + model + effort · weight: integer 1–100 · zero means disabled elsewhere

01

Status and prerequisites

This specification is the third change in the required sequence. It consumes the earlier contracts; it does not reimplement them.

OrderPrerequisiteWhat the router receives
1Quota lifecycle redesignProvider usage observations, proven drain events, reset facts, and temporary pool exclusions. No ranking score.
2Communication rebuildProvider-run identity, passive activity, truthful delivery, hold/resume, durable handoff, and typed run outcomes.
3This router refactorOne small policy reader, eligibility pass, fair selector, launch decision, and outcome attribution.
Prerequisite reconciliation. The quota draft currently permits headroom-based spawn ranking. This router forbids it. Quota may observe, hold, and temporarily exclude a pool after a proven drain; it may not continuously alter selection weights. The quota implementation must expose that narrower contract before this router lands.

02

Decisions and non-goals

The router is intentionally a dispatcher, not a planner or optimization system.

R1 / EXACTExact candidates only

Every candidate names a provider, discovered model, and effort intent. No vendor default or name-shape inference.

R2 / USERUser weights are relative

Each candidate has an integer weight from 1 through 100. Values need not add to 100.

R3 / HIVEHive means equal

Hive mode uses effective weight 1 for every eligible candidate and preserves stored user weights for later use.

R4 / FAIRNo random streaks

Smooth weighted round-robin follows the requested ratio without repeatedly hammering one route by chance.

R5 / FACTSGates filter; they do not score

Consent, discovery, fit, context, effort, entitlement, health, and proven exclusions are yes/no facts.

R6 / OUTCOMEWrong choices hand off

The router does not predict task token cost. Communication preserves work and routes a replacement after a drain or capability wall.

In scope

  • Resolve the task category to one configured candidate set.
  • Apply the existing authorized launch gates to every candidate.
  • Select with user weights or equal Hive weights.
  • Persist enough balance state to avoid streaks across restarts.
  • Emit an attributable launch decision and bounded refusal reasons.
  • Reroute a handoff while excluding its proven-drained quota pool.

Not in scope

  • Price, value, quality, benchmark, latency, or quota-headroom scoring.
  • Estimating tokens from task prose or predicting whether a run will fit in a quota window.
  • Automatically changing weights from outcomes, escalations, or memory.
  • Choosing task categories, decomposing work, or deciding handoff timing.
  • Provider launch commands, terminal state, message delivery, or recovery.
  • Ensembles, voting, shadow runs, speculative launches, or parallel attempts.

03

Architecture boundary

Each concern contributes one narrow fact. Only the selector mutates distribution state.

Ownership test. If a proposed router function reads terminal output, quota percentages, reset distance, transcript text, token counts, prices, or branch contents, it belongs in another subsystem.

04

Policy schema

A route is an explicit set of exact candidates. Order has no meaning.

type RouterMode = "user-weighted" | "hive-equal";

type RouteCandidate = {
  provider: "claude" | "codex" | "grok" | "kimi" | "opencode";
  model: string;
  effort:
    | { mode: "exact"; value: string }
    | { mode: "hive-decides" }
    | { mode: "provider-controlled" }
    | { mode: "none" };
  weight: number; // integer 1..100; preserved but ignored in hive-equal
};

type RoutePolicy = {
  mode: RouterMode;
  candidates: RouteCandidate[];
};

type RoutingPolicyV3 = {
  schemaVersion: 3;
  revision: number;
  updatedAt: string;
  provisional: boolean;
  providers: Partial<Record<CapabilityProvider, "enabled" | "disabled">>;
  models: ModelPolicy[];
  global: RoutePolicy | null;
  categories: Partial<Record<RoutingCategory, RoutePolicy>>;
};

Resolution rules

  1. An explicit model in the spawn request is a pin. It bypasses weighted selection but passes every launch gate. Hive never substitutes another model for a pin.
  2. Otherwise use the exact category route when present.
  3. If the category has no route, use global.
  4. A configured category whose candidates all refuse does not append the global route. The category was an explicit boundary, not the first half of a hidden fallback chain.
  5. If neither category nor global is configured, automatic routing refuses with never-configured.

Weight semantics

  • Weights are relative ratings, not percentages. 60, 20, 20 and 3, 1, 1 express the same distribution.
  • Weight zero is illegal. Disablement remains the explicit provider/model enablement control.
  • In user-weighted, the effective weight is the stored integer.
  • In hive-equal, every eligible candidate has effective weight 1. Stored user weights remain intact so switching modes loses no preference information.
  • The selection unit is an exact model target. If one provider exposes three eligible models and another exposes one, Hive-equal gives the first provider three aggregate shares. The UI must show that projected provider share; the router must not secretly normalize by provider.
Shared quota pools. Model-level weighting does not imply model-level quota. A proven exclusion names a quota pool; every candidate governed by that pool is temporarily ineligible together.

Every candidate is evaluated once per decision. The refusal report preserves one bounded reason per candidate so “no candidate” is actionable without exposing internal stacks or repeating the same provider failure.

06

Weighted fair selection

Weighted randomness is rejected because it permits long streaks. Smooth weighted round-robin gives bounded, deterministic distribution.

// Runs in one database transaction for one resolved route digest.
for (const candidate of eligible) {
  balance[candidate].current += effectiveWeight(candidate);
}

const selected = eligible.toSorted((left, right) =>
  balance[right].current - balance[left].current ||
  stableCandidateKey(left).localeCompare(stableCandidateKey(right))
)[0];

balance[selected].current -= sum(eligible.map(effectiveWeight));
persist(balance, launchDecision);
return selected;

Scheduler rules

  • Only currently eligible candidates receive weight in a decision. A temporarily excluded candidate does not accumulate credit while absent.
  • The balance key is a digest of the resolved route mode and candidate targets, efforts, and effective weights. A real route change starts a fresh balance; unrelated policy edits do not.
  • Ties use a stable candidate key only to make tests and diagnostics reproducible. The accumulated balance provides rotation.
  • A selection counts when Hive commits a launch decision, not when the run completes. Completion speed and outcome never feed back into weights.
  • Explicit pins do not mutate weighted balance.

07

Spawn sequence

Policy, gate, selection, and launch are separate steps with one revalidation before process creation.

If revalidation fails, that decision records launch-failed. The router excludes the failed route for this request and selects again from the remaining already-evaluated candidates, at most once per candidate. It does not fall through an ordered list.

Quota contract

Quota provides observations and proven exclusions. It never supplies a preference multiplier.

Task complexity does not become a quota estimate. A simple task may finish on little remaining usage and a complex task may not; Hive makes no speculative adjustment. If the route drains, the communication handoff is the recovery mechanism.

09

Drain and handoff sequence

Communication freezes and preserves first. Routing happens only after the handoff is durable.

A capability escalation follows the same shape but has no quota exclusion unless a separate quota event proves one. The router does not automatically “upgrade” a model or edit weights; workflow supplies a different category, requirements, or explicit model when authorized.

10

Persistence and concurrency

One small balance table makes distribution deterministic across concurrent spawns and daemon restarts.

type RoutingBalance = {
  routeDigest: string;
  candidateKey: string;
  current: number;
  updatedAt: string;
};

type LaunchDecision = {
  decisionId: string;
  requestId: string;
  policyRevision: number;
  routeDigest: string | null; // null for explicit pin
  category: RoutingCategory;
  provider: CapabilityProvider;
  model: string;
  effort: string | null;
  reason: "explicit" | "user-weight" | "hive-equal" | "fallback";
  selectedAt: string;
};

Transaction boundary

  1. Read the current policy revision and resolved route.
  2. Evaluate eligibility outside the write transaction using one inventory/availability snapshot.
  3. Begin an immediate database transaction.
  4. Confirm the policy revision and availability snapshot generation are still current.
  5. Update eligible balances, choose one candidate, and insert LaunchDecision.
  6. Commit before preparing the provider launch.
  • A stale policy or availability generation retries selection from a fresh snapshot. It never launches a decision authored against replaced facts.
  • requestId is idempotent. A retry returns the existing decision instead of consuming another fair-selection slot.
  • Balance values are bounded by normalization after each decision; integer weights and candidate count impose a small deterministic range.
  • Balance is operational state, not user preference or historical truth. Old route digests may be removed after no decision or run references them.

Policy migration

An ordered rank cannot be losslessly converted into a numeric preference. Hive must not invent how much more “first” meant than “second.”

V2 stateV3 migrationActivation
auto category with explicit fit candidatesCreate a hive-equal route containing the exact candidates and efforts.Automatic; semantics become explicitly equal.
choice ordered chainCreate an inactive migration draft preserving every target, effort, and original rank. Do not manufacture weights.The Model Control Center asks the user for integer weights, previews expected model/provider shares, then atomically activates V3.
never-configuredLeave category/global route null.No automatic routing until configured.
Provider/model enablementCopy byte-for-byte through schema validation.No new consent is created.
Historical V2 document and eventsRetain as immutable migration evidence.Never consumed by the V3 selector after activation.

Cutover rules

  • V2 remains active until every used choice route has a confirmed V3 weight set. There is no mixed V2/V3 selection inside one decision.
  • The UI may suggest weights but must label them suggestions and require confirmation. It shows normalized expected share even though stored values remain 1–100 ratings.
  • Activation is one compare-and-set mutation against the V2 revision. A concurrent policy edit invalidates the preview.
  • After activation, delete ordered-chain selection code. Do not keep a permanent compatibility router.

13

Service interfaces

The router exposes selection and inspection. It does not expose quota mutation, process control, or handoff construction.

interface RouterService {
  select(request: RouteRequest): Promise<
    | { outcome: "selected"; decision: LaunchDecision }
    | { outcome: "refused"; reason: RouteRefusal }
  >;

  inspect(request: RouteInspectionRequest): Promise<RouteInspection>;

  recordLaunchResult(
    decisionId: string,
    result: "started" | "launch-failed"
  ): Promise<void>;
}

type RouteRequest = {
  requestId: string;
  category: RoutingCategory;
  requirements: {
    reviewOfProvider: CapabilityProvider | null;
  };
  explicit: {
    provider: CapabilityProvider | null;
    model: string | null;
    effort: string | null;
  };
  handoffId: string | null;
  excludedPoolIds: string[];
};

Inspection response

inspect returns the policy revision, resolved route, effective weights, normalized expected shares, candidate evaluations, active exclusions, and current balance. It performs no selection and mutates nothing.

Integration changes

  • The spawner calls RouterService.select, then passes the exact decision to getAgentAdapter(provider).
  • The quota service no longer owns routeAndReserve. Its replacement supplies pool observations/exclusions and drain events only.
  • Communication records decisionId on ProviderRun and returns it on RunOutcome.
  • The Model Control Center edits V3 routes with revision compare-and-set and previews effective shares through inspect.

15

Acceptance tests

Distribution tests use exact counts and bounded gaps, not “looks random.”

  1. With three eligible candidates weighted 60/25/15, run 20 decisions and verify exact 12/5/3 allocation with no candidate receiving a random burst beyond the smooth schedule.
  2. Switch the same route to Hive-equal; verify equal allocation while the stored 60/25/15 values remain byte-identical.
  3. Restart the daemon halfway through a schedule; verify the combined sequence equals an uninterrupted run.
  4. Issue concurrent route requests; verify serialization produces the same counts as sequential selection and no balance update is lost.
  5. Retry one requestId; verify it returns the same decision and consumes no additional selection slot.
  6. Temporarily exclude one candidate; verify it receives no selections and accrues no catch-up burst when restored.
  7. Exclude one shared quota pool; verify every exact model governed by that pool becomes ineligible together.
  8. Vary quota percentages without creating an exclusion; verify the complete decision sequence remains unchanged.
  9. Make quota unknown or use OpenCode without a quota surface; verify the candidate remains eligible and receives its configured share.
  10. Pin an exact model; verify no substitution, no weighted-balance mutation, and the same launch gates.
  11. Configure a category route whose candidates all refuse while global has eligible candidates; verify Hive reports category refusal and does not silently append global.
  12. Remove the category route; verify global then becomes the resolved route.
  13. Fail a selected route before provider start; verify one launch-failed decision, cooldown activation, and a bounded retry among remaining candidates.
  14. Drain a running route with a near reset; verify communication holds/resumes the same run and router selection is not invoked.
  15. Drain a running route with a far reset; verify handoff is durable before a replacement route request and the drained pool is excluded.
  16. Force every candidate ineligible; verify one bounded reason per target and no fallback to a disabled, unknown-consent, or out-of-policy model.
  17. Attempt to migrate a V2 ordered choice without user weights; verify V3 stays inactive and every original target, effort, and rank remains inspectable.
  18. Add a sixth provider to CapabilityProvider; verify policy validation, inventory evaluation, factory registration, and provider conformance fail until the provider is handled.
  19. Assert the router module has no imports from terminal observation, provider transcripts, token accounting, price data, git worktree inspection, or message delivery.
