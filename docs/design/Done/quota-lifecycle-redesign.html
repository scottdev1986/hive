00 · Verification basis

Hive quota lifecycle

A present-tense map of how Hive measures provider usage, what that measurement is allowed to decide, how a mid-work drain is classified and handled, and where quota's authority ends. Every factual claim carries the rung of evidence that stands behind it and, below the top rung, the exact check that would raise it.

Quota does not refuse a launch for usage. The launch gate's five refusals — resolution, enablement, availability, capability-floor, effort — contain no usage check, and routeAndReserve contains no headroom veto. Exhaustion is a mid-work condition handled by the drain handler. Two refusals do still originate inside quota's call, and neither is about usage: a request naming a provider that has no route for the category, and a ledger whose persisted history cannot be read. §05 states both exactly.

The deployed system is not this source. The installed CLI reports hive 0.0.38 (8ff0a55f, 2026-07-24, darwin-arm64); git rev-list --count 8ff0a55f..1a0c9708 printed 113. The running daemon's build was not measured for this document, so no claim here rests on it being current. The live rows below are readings taken from the running daemon and its quota.db; they establish that the serving system behaves as described, not that it is built from this commit.

Evidence rungs

  • TESTAn in-process test exercises it. The row names the test.
  • PROCESSA real process, PTY, or signal was exercised. The row names it. This is strictly stronger than test and is never flattened into it.
  • VENDORA real vendor CLI or binary was in the loop. The row names the command and version.

  • UNPROVENImplemented, with nothing exercising it at any rung. The row names the observation needed.

02

Authority discipline

What a quota number is permitted to cause, and what it is not.

  • TESTA usage number never refuses a launch. AuthorizedLaunch.gate runs exactly five guards in fixed order — resolution, enablement, availability, capability-floor, effort — and none reads a pool. routeAndReserve requires an already-gated AuthorizedLaunch for every candidate and adds no usage test of its own. src/daemon/authorized-launch.ts: AuthorizedLaunch.gate; src/daemon/quota.ts: routeAndReserve, requireAuthorizedLaunch.Drive a live spawn against a provider whose pool reads 0% remaining: the agent launches, and the returned decision names that provider.
  • TESTAn unmeasured window is unknown, never empty. drainedWindowFor skips any window whose availability is not available and any whose remainingPct is null; only a measured value at or below zero drains. Test: test/daemon/drain-handler.test.ts — a measured window at zero drains, an unknown or unmetered one never does.On a restarted daemon, disable one provider's probe, let its reading go missing, and confirm no agent on that provider is held.
  • TESTA provider that will not answer never becomes a fabricated number. The refresh records the failure reason in probeErrors, reports the provider unavailable, and leaves the last real observation in the ledger with its own timestamp and provenance. src/daemon/quota.ts: refreshFromProviders. Live confirmation is the §04 row.
  • TESTEvery reservation is Hive's own workload guess and is labelled one. estimateFor reads DEFAULT_PERCENT_ESTIMATES per routing category for percent pools and a flat 10 units for unit pools; no provider supplies these. src/schemas/quota.ts: DEFAULT_PERCENT_ESTIMATES; src/daemon/quota.ts: estimateFor. Live confirmation: every pool in hive_quota_status reports reservedIsEstimate: true.
  • TESTRoute health is failure evidence, not usage, and it is a cooldown rather than a ban. quarantinedUntil reads QuotaLedger.routeHealth; a route that just failed to produce a working agent is passed over for launchQuarantineMinutes (default 15). If every candidate is quarantined the code launches anyway and says so in a warning rather than refusing.   • TESTSelection never compares unlike windows. reserveFairGroups ranks by weighted-fair dispatch deficit computed from quota_fair_dispatch history; quota percentages do not enter the comparison at all, so a provider with no meter needs no invented headroom score. Tests: test/daemon/quota.test.ts — fair dispatch starts with the stable primary instead of comparing unlike headroom windows and — sole-capable assignments create no fairness debt.Spawn repeatedly across two live providers with very different remaining percentages and count the dispatches: they converge on equal share, not on headroom share.

05

Routing and booking

routeAndReserve chooses a candidate and books it. It does not gate.

The walk

TESTEvery candidate must already be an AuthorizedLaunch. The request is then narrowed twice — to explicitTool when the caller pinned a provider, and away from reviewOfTool when the category is code_review — after which each surviving candidate is evaluated into its governing pools. A candidate whose pools yield no measured entry is marked unknown and carries an empty entry list; it is not warned about and not treated as a special mode. Route health then partitions the list into viable and quarantined, and if every candidate is quarantined the whole list is attemptable anyway. src/daemon/quota.ts: routeAndReserve.

TESTspread hands the attemptable list to QuotaLedger.reserveFairGroups, which atomically picks by dispatch deficit and books the winner in the same transaction; concurrent spawns therefore land on different providers. strict takes the first attemptable candidate in rank order and books it through reserveGroupUnchecked. Both paths always return a decision. Tests: test/daemon/quota.test.ts — atomic fair dispatch gives concurrent spawns different providers; — strict mode preserves chain order despite unequal headroom; — routes review to the other vendor when quota is equally healthy.Launch two live agents simultaneously in spread and read their providers: different, and the quota_fair_dispatch table gains one row each.

08

Hold and the resume wake

A hold pauses a real process and records what would make resuming it safe. There is one kind of hold, and it is always a wait the sweep can end.

Taking the hold

TESThold requires an active provider run and a successful pause of that exact run; if either is missing it returns false and the caller falls through to the replacement seam with the reason extended to say the source could not be held. On success it writes four fields to the agent row in one upsert: status: "held", holdReason, holdResetAt, and holdProviderRunId. The pause itself is the terminal host's verified group signal, not quota's. src/daemon/drain-handler.ts: hold. Test: test/daemon/drain-handler.test.ts — §R4: a drain resetting within the hour holds the agent, and the sweep pokes it past the reset, which asserts the status, the reason text carrying both the pool name and the reset time, the reset field, and the pause call.Drain a live route with a near reset and read the agent row plus ps -o stat for its group: held with the reset time and run ID, and every non-leader member in state T.

TESTEvery hold carries the reset it waits for. hold takes a required string reset time, so the two arms that call it — a measured window resetting within the hour, and the all-drained wait on the nearest reset — are the only ways an agent becomes held, and both give the sweep's resume branch the non-null reset it needs. No reset is invented to satisfy that branch: an arm with nothing to wait for does not hold at all. The replacement seam and the all-drained arm with no wait target hand the agent to the seam, which freezes it under control-paused with its terminal, worktree, and branch retained (§09). Tests: — a drain with no reset to wait for never leaves the agent held, which drives a live working agent through a distant-reset drain and asserts the row is not held with a null reset; — §R6: no near reset anywhere preserves the branch and writes the memory, which asserts the same of the retain arm alongside the intact worktreePath and branch.

What is revalidated before the one wake

The resume runs entirely inside the maintenance sweep. Seven conditions are checked in this order, and every one of them can silently abandon the resume, leaving the agent held for the next tick:

#RevalidationWhy it is not redundant
1Refresh that provider's quota firstThe reset time is a vendor prediction. Resuming on a predicted reset without re-reading would wake an agent into an empty meter.
2Re-read the agent; it must still be heldThe row read at the top of the sweep is stale by the time the refresh returns; the agent may have been killed or handed off in between.
3drainFor must now return nullThe reset passing is not the same fact as the usage returning. A provider that reset into a still-spent window does not wake anyone.
4An active provider run must existA held agent whose process died has nothing to continue.
5holdProviderRunId must equal the active run IDWaking a different run than the one that was paused would resume a process this hold never fenced.
6capabilityEpoch must equal the run's epochAn epoch revoked while held means authority was withdrawn; the wake would hand work to a run that may no longer write or land.
7The resume signal must succeedThe terminal host verifies foreground identity before SIGCONT. A failed resume must not be followed by a message telling a stopped process to continue.

TESTConditions 3, 5, and 6 are each driven to failure and back in one test: test/daemon/drain-handler.test.ts — §R4: a drain resetting within the hour holds the agent, and the sweep pokes it past the reset observes a still-drained provider, then a drifted holdProviderRunId, then a drifted capabilityEpoch, asserting no resume each time, and only then the successful wake. After the wake it asserts the agent is idle with all three hold fields cleared, and that a further sweep produces no second resume and no second message. src/daemon/drain-handler.ts: resumeHeld.

UNPROVENExactly one wake reaches the agent — proven in halves, never end to end. The handler's half is real and tested: it emits one message with the stable idempotency key quota-resume:<agentId>:<runId>:<holdResetAt>, and test/daemon/drain-handler.test.ts — overlapping reset sweeps produce one idempotent wake drives two concurrent sweeps through a barrier so both reach SIGCONT, then asserts one message with that key. But the de-duplication in that fixture lives in the harness's own send stub, so the test proves the key is stable and passed, not that anything honours it. The production honouring is implemented and separately reasoned: MessageDelivery.send looks the key up across the sender's aliases before inserting and falls back to the same lookup when the unique index rejects the insert (src/daemon/delivery.ts: send), and that mechanism is exercised for control messages by test/daemon/control-messages.test.ts. Nothing exercises the quota-resume key through real delivery.On a restarted daemon, hold a live agent, force two overlapping maintenance ticks across its reset, and count rows in the message table with that idempotency key: exactly one.

TESTRepeating SIGCONT on an already-verified group is accepted as harmless; the durable message key, not the signal, is the once-only boundary. The same overlapping-sweep test asserts two resume calls and one message.

09

Replacement seam

Everything up to and including a durable, pickup-ready handoff exists. The launch does not.

NOT IMPLEMENTEDNo code selects or launches a replacement agent after a drain. replaceWithHandoff ends by sending the root a durable notice carrying the provider, the pool, the reset time, the handoff ID, and the drain reason, keyed handoff-awaiting-route:<handoffId>, and stops. The gap is marked in the source as TODO(router). Implementing it requires an owner that accepts a measured provider/pool exclusion and returns either a launch decision or a durable no-candidate outcome; quota supplies the exclusion, it does not choose. src/daemon/server.ts: replaceWithHandoff.Nothing to observe until the edge exists. The nearest positive check is reading a live drain notice: it carries no launch decision and no replacement agent appears.

What the seam does do, in order

TESTPreconditionsThe agent's most recent provider run is required; without one the call raises and says the terminal and worktree remain retained. A handoff already existing for that source run returns immediately, so the seam is idempotent per run.

Unmetered providers
