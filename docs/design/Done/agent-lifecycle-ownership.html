Design record

Agent lifecycle ownership

Spawning an agent should be a process launch that returns a handle. Until 2026-07-28 it was a negotiation across four components in which a terminal was killed unless something kept telling it to live, once every five seconds, per terminal. That inversion caused three fleet collapses. This document records what was there, what replaced it, what the replacement measured, and what is still open.

The invariant, stated once. A terminal is alive if and only if its process is alive. Liveness is observed, never maintained. Failing to attach, render, publish, or renew must never change whether an agent lives.

History

1. What was there

A single hive_spawn traverses six layers and ends in three processes: a sessiond host, a login zsh on a PTY, and the vendor TUI running beneath that shell. The orchestration lives in spawnReserved (src/daemon/spawn/spawner-impl.ts). That part is unchanged.

What changed is the loop that ran beside it. Every five seconds the daemon walked the Workspace's published inventory and sent one broker RPC per terminal to renew a fifteen-second lease. A terminal that missed its renewals was terminated by sessiond — so terminal liveness depended on message delivery, on the same loops the spawn burst was saturating.

Fixed budgets that did not scale with burst width

All four are constants in src/schemas/session-protocol.ts.

attachGrantTimeoutMilliseconds30 sViewer attach grantunchanged

Spawn cost scales with N. The lease did not. Past some width the pipeline from “host created” to “first renewal landed” exceeded 15 s and the fleet died.

Root cause

2. The lease inversion

The conflation. One 15-second timer decided two completely different things:

“my supervisor is gone” — rare, and it looked like it should be fatal.
“a renewal was late” — common under load, entirely benign.

Every collapse was the second being treated as the first. §7c goes further: the first is not fatal either. Neither reading is evidence about the agent.

The signal already existed, one level up

brokerOwnerIsLive (native/sessiond/src/broker.zig) is a pid + start-token comparison against the daemon, evaluated at the top of every iteration of the serve loop. sessiond already knew, continuously and in O(1), whether the daemon was alive — on a path nothing can starve. 

fn brokerOwnerIsLive(owner: BrokerOwner) bool {
    const observed = inspectProcess(owner.pid) catch return false;
    return std.meta.eql(observed.start_token, owner.start_token);
}

What the per-terminal lease actually added was only the killing: sessiond noticed the daemon died and returned from serve(), but hosts are separate forks that reparent to launchd and keep burning tokens. The lease was how they eventually died. Real work — but answered per terminal, by message, when it could be answered once, by observation.

The measurement that redirected this work. An out-of-process probe of the daemon's HTTP surface recorded a worst-case latency of 1.6 s through the entire 31-agent burst. The daemon was never stalled. The standing explanation — “the daemon's event loop is saturated” — was wrong. What timed out was the publish endpoint specifically, because it awaited one broker round trip per terminal before replying, under the Workspace's fixed 5 s timeout.

Design

4. Ownership

The organising principle is mechanism versus policy, and the second rule the user named: the terminal must not depend on spawning, and spawning must not depend on the terminal. A terminal may make itself easy to observe; nothing may make it wait.

ComponentOwnsMust not own
daemon Policy. Who exists and when they die. Agents, worktrees, quota, briefs, recovery decisions. PTYs, file descriptors, process trees, keeping anything alive
sessiond Mechanism. PTYs, process tree, durable records. Survives daemon restarts. Reaps on observed daemon death. Whether an agent should exist
host Its own dead-man switch: watches its supervisor's pid directly, and publishes its own liveness. Anything about other hosts; anything about a spawn's progress
Workspace Rendering and input. Attaches and detaches freely. Anything about lifecycle
Record

5. What was implemented

Four changes, in this order. Each is independently valuable and was measured against the rig before the next landed.

  1. A mutex in ProductionHostLauncher (native/sessiond/src/host_runtime.zig). The broker serves one connection per thread and deliberately releases its state gate around launch and finalize, because both are slow and touch nothing shared. They did touch the launcher: two concurrent creates could hand out the same pending id, append to clients at once, or remove an entry from under another thread's index. Finalize now claims its client under the gate and removes by identity rather than by a stale index, so the slow work still runs concurrently.
    Not a revert of the concurrent accept loop. That loop is what stops one CREATE_COMMIT from holding the accept loop through an entire host launch; removing it would restore the head-of-line blocking it was added to fix.
  2. Liveness by observation. The host records its supervisor at boot (getppid() plus that process's start token) and re-binds it whenever a broker proves the 32-byte adoption secret. Lease expiry kills nothing, and a running host holds its own lease open.
    Superseded (§7c): the host originally terminated itself once its supervisor had been continuously absent for a grace window, writing SUPERVISOR_GONE. That path is now removed. A host that cannot observe its supervisor is not evidence that the agent inside it is dead, and the reaping argument that justified it — that not killing leaks N hosts per daemon crash — turned out to cost more than the leak: it was one of six paths killing live, working terminals. Orphan cleanup belongs to an explicit sweep, not to a host's guess about its parent.
  3. The broker reaps on observed daemon death. Superseded (§7c): Registry.terminateAll stopped every registered host when the broker saw its daemon exit. Removed for the same reason: the broker's daemon being gone says nothing about whether an agent's terminal is alive and working. The broker now stops serving and leaves the hosts running.
  4. The renewal fan-out is gone. No 5 s timer, no per-terminal RPC, no create-time self-renew, no expiry audits, no renewVisibility on the daemon at all. What remains of the Workspace loop is a watchdog that shuts the daemon down when the Workspace it serves is gone — policy the daemon owns, and nothing a terminal depends on.

Two things the lease had been hiding

Removing it exposed a second bottleneck that had never been reached, because the fleet used to die of the lease first.

The spawner supplies only AgentTurnInput: a way to write to one agent's terminal, fenced by the foreground identity that launch established, carrying no vendor knowledge and no if (tool === …).

Honesty

7. What is not closed

31 wide holds. 1, 2, 4, 8, 16 and 31 all reach 31/31 alive, 31/31 with a live host, repeatably. Getting there took three separate corrections, and the order matters because each was hidden by the one before it: the six paths that killed terminals on an inference (§7c), the broker that stood between Hive and its terminals (§7d), and two more fixed budgets that did not scale with load. Note the discipline the numbers still demand: an 8-wide run launched straight after a 31-wide one returned 4/8, and the same width on a swept, idle machine returned 8/8. Every figure here is worth only as much as the sweep that preceded it — and only as much as the instrument, which reported zero live hosts while four were provably running.

Two measurements bounded it while the broker still existed. Creates were healthy at 16 wide — 0.3–1.4 s in the broker against a 10 s budget — and took 12.3–14.3 s at 31, not because the broker got slower but because thirty-one vendor CLIs starting at once is what each new host competes with for the machine. Raising the create budget to 60 s took 31 wide from 5/31 to 21–24/31, and what remained was HELLO timing out: the broker's accept loop was not reaching new connections in time. A create is no longer a held RPC and there is no accept loop to reach (§7d), so neither budget governs anything now.

A hypothesis this rig disproved, recorded because the reasoning was wrong. Bad runs all contained sessiond broker exited 143 — SIGTERM — and good ones did not, so the broker dying mid-burst looked like the discriminator. The daemon was ruled out (its supervisor suppresses the restart path for exits it initiated) and so was the memory watchdog (it walks descendants of each terminal's shell root; the broker is their parent), which left an unexplained external killer and a plausible story about hosts dying with it.

The kernel settles it. The broker now reports si_pid on the signal that kills it, and the answer is the rig's own teardown: a pid lower than the daemon's, firing at log line 44 of 53. The broker's death is an artifact of tearing the run down, not a cause of anything. The correlation was real and the inference from it was not.

The supervisor grace was raised from that inherited 15 s to 90 s on the strength of that wrong story. It is now moot: the host no longer self-terminates when it cannot observe its supervisor at all (§7c). A host that cannot see its supervisor is not evidence that the agent inside it is dead.

Two starvation sources were found and fixed after the create budget, and both moved the number: the serve loop took the shared state gate twice before it polled, so a worker busy with a create delayed accepting connections that were already pending — that was the HELLO timeout, and moving both janitorial passes onto a 250 ms cadence took spawn-path HELLO timeouts to zero. Then the spawn's own wait for the provider's foreground process, a fixed forty polls of 25 ms, was scaled and given a backoff: raising the window alone made things worse (7/31), because thirty-one spawns asking every 25 ms for thirty seconds are themselves a large share of the load they are waiting on. With the backoff the same run returned 28/31.

The lead that remains, named and unproven: the broker holds one global state gate across operations that do IPC to a host, so a single loaded host can block every other broker operation — including the accept loop's own bookkeeping. Making that bookkeeping skip the gate when it is busy was tried and reverted: reapExitedHosts is the only path that returns registry capacity, and skipping it under contention produced ALREADY_EXISTS failures. The gate should instead be released around host IPC, exactly as launchHost already releases it around launch and finalize.

The redesign is what makes any of this tractable: waves are free now. Under the lease, an agent created in the first wave had 15 s to be renewed, so queueing later creates behind it killed it. Nothing renews anything today, so an agent waiting its turn costs latency and nothing else — create concurrency can be tuned for throughput rather than against a deadline nobody can meet.

Measurement conditions. These runs share one laptop with an editor, a browser, and other agents; cmp was killed by the OS during one build. The 31-wide spread is partly that. A quiet machine is the first thing the next measurement needs, and leftover vendor processes from a previous run must be swept before the next — they were, twice, and the numbers moved.

Attempted and removed

7b. Why the terminal does not yet report

The daemon establishes a provider's foreground identity by polling INSPECT up to forty times per spawn, and every poll costs the broker a fresh unix-socket connection to the host and an RPC — roughly twelve hundred host RPCs for a thirty-one wide burst. The fact belongs to the host: it owns the PTY master and measures the foreground process group with tcgetpgrp. Asking forty times is the same inversion the lease had.

A push implementation was built on 2026-07-28 and then removed. It is recorded here because the reasons it failed are the design constraints for the next attempt.

What the attempt got right

Nothing needed to be added to the wire. EVENT (0x0209) already exists and protocol.zig already classifies it as unsolicited; wire_schema.session_event is already generated from the frozen SessionEvent. The broker's control socket already refuses any clientRole but daemon, so HELLO is the subscription — no new frame, no codegen, no fixture churn. Any future attempt should start from this.

Why it was removed

It replaced polling with polling. Because no host→broker push channel exists, the broker had to discover the foreground itself: a watcher thread calling INSPECT against every pending host four times a second. That is the same inversion in a new place, and it carried a thread, a ring buffer, per-connection cursors and a retention set purely to compensate for the missing channel.

The producer half worked and was proven on the wire — 27–32 reports published at 31 wide with real foreground pgids, frames written, and the daemon's decoder accepting them. The spawn never once acted on a report: instrumented at 31 wide the wait was reached 26–31 times and returned false every time. Retaining reports for late subscribers was the leading theory and did not move the number, so that is not the explanation, and the gap was never found. It bought nothing and cost a background poll, so it came out.

The constraint for the next attempt

Resolved by §7d, and worth recording why it looked impossible. Every reporting design here degenerated into polling for one reason: the host had nowhere to speak to. Removing the broker inverted the connection — Hive listens, the host dials — and holding that stream open after registration is the channel, at no extra cost. The constraint below was real; it was a property of the broker, not of terminals.

There was no host→broker channel. The neutral host RPC (neutral_runtime.zig Client.call) opens a fresh unix socket per call and closes it; the host's registration stream is closed after READY; and the broker's control socket authenticates clientRole: "daemon" only, so a host cannot connect to it. Until the host can speak to the broker unprompted, every “reporting” design degenerates into someone polling on the host's behalf.

Build that channel first. The report itself is then event-driven off PTY output the host already reads — compare tcgetpgrp to the shell's group, send one frame, once — and the broker becomes a relay rather than an observer.

Root cause

7c. Hive was killing its own working agents

The 31-wide forensics found hosts SIGKILLed with failureCode: null, panes showing fully rendered vendor TUIs, and zero termination audits in the binding store. No lease, no supervisor, and no crash explained it.

The spawn was the killer. When the daemon could not observe a provider's foreground identity inside its window, createSession called terminate(mode: "immediate") and threw. Not having seen the provider was being treated as evidence the provider had failed. It is not. The error text was literally "terminal cleanup was not confirmed" — the terminate itself threw partway, so the kill landed and the audit never got written. That is the missing-audit mystery, start to finish.

What it exposed underneath

With the killing gone, the remaining 31-wide failure is a different problem that the killing had been masking: only 15 host directories existed for 31 admitted agents. Sixteen creates never happened at all, failing with sessiond HELLO request timed out — the broker would not accept connections during the burst. No agent dies there; half of them are never created. That is accept-loop capacity, and it is the next thing to fix.

Landed

7d. The broker is gone; Hive owns its terminals

31 wide holds. 1, 2, 4, 8, 16 and 31 all reach 31/31 alive, 31/31 with a live host, repeatably, with no broker process anywhere. The spread that ran 8–28 on identical binaries is gone, because the thing producing it is gone.

What the broker actually was

One process per HIVE_HOME, standing between Hive and every terminal, with one accept loop and one state gate. It was never in the terminal data path — a viewer has always connected straight to host.sock — so on the control path it was a relay: it handed a socketpair to a forked child, and it proxied INSPECT by opening that same socket itself. Under thirty-one simultaneous launches its connection threads parked inside multi-second vendor boots and stopped accepting, so sixteen of thirty-one creates died at HELLO without ever starting.

The inversion

The host now dials a control socket named by HIVE_HOST_CONTROL_SOCKET instead of only inheriting descriptor 3. That one change is what lets a launcher which is not a forking C parent start a terminal, and it is backward compatible — an inherited descriptor still works. Everything after the dial is the same private stream the broker used, so every byte of the boot handshake is unchanged.

The terminals were never unhealthy; the file that made them visible was not being written. A measurement that disagrees with the process table is wrong about the world, and this rig has now been wrong three times in one day.

Budgets that did not scale

Two more copies of the lease's defect turned up once the terminals survived long enough to hit them. The MCP reporting gate refused any agent whose vendor had not authenticated within 15 s of launch — measured against one agent on an idle machine, and expiring constantly when thirty-one vendors boot at once. And the kickoff fenced its first keystroke to the foreground identity captured the instant the vendor appeared, which a vendor that spawns its own child immediately invalidates. Both now scale or re-measure rather than failing an agent whose terminal is alive and drawing.

What is left

broker.zig remains on disk because the host links several of its helpers, but nothing runs it: the serve role is deleted, the supervisor is deleted, and SessiondHost holds no broker transport at all. The residual flake is an input-claim race at kickoff, not a terminal death — every terminal is alive when it happens.

Evidence

7e. The live 16-agent run: spawning was never the problem

A queen launched sixteen no-op agents on a live instance. All sixteen were admitted, all sixteen got a host, and the daemon log recorded no launch failure of any kind. What went wrong happened after the terminals were up, which is why a spawn-side reading of it found nothing.

Nine agents alive and unreachable

The daemon could not deliver a message to nine of the sixteen. Every one of them was live and idle. The host answered every retry with idempotency key reused with different input — and the input was byte-identical every time.

The host's replay ledger keyed an input's identity on the claim token. A claim token is minted fresh by every CLAIM_ACQUIRE that finds no live claim, and the daemon releases its claim when each submit cycle closes — so a resend always arrives under a brand-new token, and the ledger called it different input. The condition could not self-correct: every further attempt minted another token. Identity is now scoped to the writer, which is stable across attach cycles and still keeps one viewer from reading back another's receipt.

The queen's own hypothesis — that a shared owner token hive-daemon:<instance> collided keys between agents — was wrong, and worth recording as wrong: the daemon is legitimately one writer, and each agent has its own host process with its own ledger. The collision was always inside a single agent's ledger.

A dead host could not be closed by any tool

hive_kill and hive_mark_dead both refused with sessiond locator has no terminal-host binding, because terminate required the host to still be listed. Both close paths therefore depended on the very thing whose absence they were called to clean up, and the agent row stayed live forever holding a quota reservation and collecting undeliverable messages. A host this instance owns but can no longer see is now reported as already terminated — with SESSIOND_HOST_ALREADY_ABSENT and a null exit, because nobody watched it leave. Ownership is still enforced; absence excuses a missing host, never a missing claim to it.

The readiness gate was reasoning blind

Two opencode agents were failed for "no sign of life for 12 s (screen never redrew…)". The screen was never read at all: captureVisible throws unconditionally on the sessiond path, so the pane signal cannot fire, and of the gate's four signals only the process check is available to a vendor with no hook wiring. The verdict was nonetheless correct — both agents stopped at exactly 3560 output bytes, an identical TUI prologue, then silence for twenty minutes, while the third opencode agent passed 8815 and kept going. The reason string now says the screen was never readable rather than claiming an observation nobody made.

Two of three concurrent opencode instances dying identically after TUI initialisation is a vendor-level startup collision, not a terminal defect. It is left named rather than worked around.

A worktree removed after a kill said keep

Reconciliation removed a worktree about fifteen seconds after a hive_kill that kept it. This is the designed behaviour, not a regression: the worktree had no unmerged commits and no real uncommitted paths, and reclaiming exactly those is what the sweep is for. keepWorktree scopes that one kill, not the repository's future; durable intent is hive_preserve_branch, which nothing in the run used. Recorded because the flag reads like a promise it does not make.

One real defect did surface next to it: opencode's provisioned .opencode/plugins/hive-turn-events.ts was missing from the discounted-wiring list, so every opencode worktree counted as carrying real uncommitted work and could never be swept. The path is now derived from the constant the writer uses.

Decisions

8. Rejected and deferred

ProposalDisposition
rejected Revert the concurrent broker accept loop as step 1 The race it exposed is real and is fixed with a mutex. Reverting the loop would restore the head-of-line blocking that made a wide burst unsurvivable in the first place
rejected Make lease expiry non-fatal first, add reaping later Every daemon crash in between would leak N hosts, N shells and N vendors permanently. Merged into one conditional change instead, so the safety property holds at every instant
deferred Show the pane first: fork zsh immediately and submit the provider command into the running shell instead of baking it into argv Fixes no collapse, and costs more than it looks. Provider identity is established by polling for a new foreground process and recorded as the run's pid, start token and process group; input arbitration, readiness and hook attribution all key off it. Submitting the launch command would mean arbitrating input against the shell and then re-establishing identity afterwards — a new state machine in the subsystem with this repo's worst defect history. argv cannot fail to arrive; typed input can. Separately, the pane cannot appear before its worktree exists, so “tens of milliseconds” was never the real target
rejected Have the host wait for the provider to take the PTY foreground before it reports READY, so the create's own answer carries “the TUI is up” Right idea, wrong place. The wait sits inside the create, and a create holds an admission slot — so vendor startup serialised four at a time and creates hit their ceiling. Measured 10/31 against 23–28 without it. The readiness signal has to arrive after the create returns, which means the event channel below, not a longer create
next Let the terminal report its own status instead of being polled for it. SessionHost.subscribe(afterEventSeq) is already in the frozen contract, declared and never implemented This is the root of what is left. create returns when the shell is exec'd — before the profile is sourced and the vendor exec'd — so the one fact the daemon needs is not knowable when its handle comes back, and nothing tells it later. So it asks: forty INSPECTs per spawn, each a broker round trip holding the state gate, which at thirty-one spawns is a large share of the load being waited on. The host already knows the answer for free: a foreground job is tcgetpgrp against the shell's own process group, one local syscall.
